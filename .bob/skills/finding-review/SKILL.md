# Finding Verification Skill

## Purpose

This skill independently verifies findings generated by PR Guardian review specialists.

Its purpose is not to discover as many new issues as possible.

Its purpose is to determine whether existing findings are supported by reproducible, deterministic, or directly inspectable evidence.

The verification layer increases review confidence and reduces false positives before findings are included in the final Pull Request review.

---

# Core Principle

Do not accept a finding merely because another AI reviewer produced it.

Use:

```text
finding
   ↓
verification strategy
   ↓
evidence collection
   ↓
result
   ↓
confidence update
```

The preferred outcome is:

```text
Don't just comment.
Prove it.
```

---

# When to Use

Use this skill after one or more review skills produce findings.

Prioritize verification for:

* CRITICAL findings;
* HIGH findings;
* security findings;
* authorization findings;
* data integrity findings;
* API breaking changes;
* queue idempotency issues;
* regression risks;
* findings suitable for executable tests.

Verification may be skipped for purely informational observations.

# Verification Status

Every reviewed finding must receive one of:

```text
VERIFIED
UNVERIFIED
NOT_APPLICABLE
VERIFICATION_FAILED
REFUTED
```

Definitions:

## VERIFIED

The finding is supported by direct evidence, deterministic analysis, or reproducible behavior.

## UNVERIFIED

The finding remains plausible, but available verification was insufficient.

## NOT_APPLICABLE

The finding does not require executable or additional verification.

Example:

A directly visible OpenAPI mismatch may already be self-evident.

## VERIFICATION_FAILED

Verification was attempted but could not be completed because of environment or tooling limitations.

## REFUTED

Verification produced evidence that contradicts the finding.

Refuted findings must not be published as defects.

# Phase 1 — Load Findings

Load all candidate findings.

For every finding collect:

```text
id
category
severity
confidence
title
description
file
line
evidence
recommendation
verification_status
```

Do not mutate the original finding artifact.

Verification results should be stored separately.

---

# Phase 2 — Prioritize Findings

Verification priority should generally be:

```text
1. CRITICAL
2. HIGH
3. security-sensitive MEDIUM
4. data-integrity MEDIUM
5. breaking-change MEDIUM
6. other actionable findings
```

Do not spend significant resources verifying low-value informational findings.

---

# Phase 3 — Select Verification Method

Choose the lowest-cost reliable method.

Possible methods:

```text
DIRECT_CODE_EVIDENCE
EXISTING_TEST
GENERATED_REGRESSION_TEST
STATIC_ANALYZER
TYPE_CHECKER
SECURITY_ANALYZER
DEPENDENCY_ANALYZER
API_SPEC_COMPARISON
MIGRATION_EXECUTION
DATABASE_INTEGRATION_TEST
QUEUE_EXECUTION_TEST
MANUAL_REPOSITORY_TRACE
```

Prefer deterministic methods where available.

# Verification Strategy Selection

Example:

```text
Finding:
Possible cross-tenant access

Best verification:
Generated regression test
```

Example:

```text
Finding:
OpenAPI does not document 409

Best verification:
Direct implementation/spec comparison
```

Example:

```text
Finding:
Possible SQL injection

Best verification:
Direct data-flow inspection + Semgrep
```

---

# Phase 4 — Direct Code Evidence

Some findings can be verified without execution.

Example:

```text
Implementation:
return 409

OpenAPI:
documents only 201, 400, 401
```

This can be:

```text
VERIFIED
```

through direct evidence.

Record exact supporting files and lines where possible.

---

# Phase 5 — Existing Test Verification

Before generating a new test, check whether an existing test already proves or disproves the finding.

Example:

```text
Finding:
Expired API keys may still work.
```

Search for:

```text
test_expired_api_key
```

If the test exercises the same path and passes, inspect whether the finding is refuted.

---

# Phase 6 — Generated Regression Test

When a finding is behaviorally testable, generate the smallest useful test.

Workflow:

```text
finding
   ↓
identify precondition
   ↓
build synthetic setup
   ↓
execute changed behavior
   ↓
assert expected safe behavior
```

---

# Regression Test Requirements

Generated verification tests must:

* be deterministic;
* use synthetic data;
* avoid production systems;
* avoid destructive side effects;
* isolate the suspected behavior;
* contain meaningful assertions;
* fail for the suspected defect.

Do not write broad tests covering unrelated functionality.

---

# Temporary Test Location

Prefer:

```text
reports/verification/<pr-id>/tests/
```

or an isolated temporary workspace.

Do not silently add generated tests to the repository's permanent test suite.

Permanent adoption requires explicit implementation work.

---

# Example — Authorization Verification

Finding:

```text
Cross-tenant resource access may be possible.
```

Verification setup:

```text
Organization A
  User A
  Token A

Organization B
  Resource B
```

Test:

```python
response = client.get(
    f"/resources/{resource_b.id}",
    headers={"Authorization": token_a}
)

assert response.status_code in {403, 404}
```

If actual result is:

```text
200
```

the finding becomes:

```text
VERIFIED
CONFIRMED
```

---

# Phase 7 — Static Analysis

Use static analyzers when appropriate.

Examples:

```text
Ruff
mypy
Bandit
Semgrep
```

Tool output is evidence, not absolute truth.

---

# Ruff

Use Ruff primarily for deterministic correctness or code-quality signals where relevant.

Example:

```bash
ruff check .
```

Do not use lint-only output as proof of a behavioral defect unless clearly related.

---

# mypy

Use type checking when the finding involves:

```text
incorrect return type
nullable access
incompatible argument
interface mismatch
```

Example:

```bash
mypy app/
```

Do not assume absence of mypy errors proves runtime correctness.

---

# Bandit

Use for security-sensitive Python patterns.

Example:

```bash
bandit -r app -f json
```

Preserve:

```text
reports/raw/<pr-id>/bandit.json
```

---

# Semgrep

Use for:

```text
source-to-sink security paths
dangerous APIs
known security patterns
```

Example:

```bash
semgrep scan --config auto --json
```

Preserve raw output separately.

---

# Phase 8 — Dependency Verification

Use dependency tools when findings involve vulnerable packages.

Examples:

```text
pip-audit
```

Store evidence.

Distinguish:

```text
introduced by PR
pre-existing
```

A pre-existing dependency issue should not be blamed on the PR unless the PR changes or exposes it materially.

---

# Phase 9 — API Verification

For API contract findings, compare:

```text
implementation
vs
OpenAPI / Swagger
```

Verify:

```text
route
method
status code
request schema
response schema
authentication
```

Example result:

```text
IMPLEMENTATION:
POST /users returns 409

OPENAPI:
409 missing

Result:
VERIFIED
```

---

# Phase 10 — Database Verification

For database findings, use isolated environments only.

Possible methods:

```text
migration execution
constraint test
transaction test
EXPLAIN
integration test
```

Never run destructive verification against production.

---

# Migration Verification

Preferred workflow:

```text
create isolated database
      ↓
apply base migrations
      ↓
insert synthetic existing data
      ↓
apply PR migration
      ↓
inspect result
```

Example:

```text
migration adds NOT NULL organization_id
```

If migration fails with existing records:

```text
VERIFIED
```

---

# Phase 11 — Queue Verification

Use isolated queue infrastructure when needed.

Possible methods:

```text
RQ synchronous mode
test Redis
test broker
framework worker utilities
```

Verify:

```text
retry
timeout
duplicate execution
idempotency
failure behavior
```

Never enqueue verification work in production.

---

# Example — Retry Idempotency

Finding:

```text
Payment job may double-charge after retry.
```

Verification approach:

```text
mock payment provider
fail after first successful charge
retry same job
count provider calls
```

If provider call count becomes:

```text
2
```

finding may become VERIFIED.

---

# Phase 12 — Concurrency Verification

Use concurrency tests only when necessary.

Potential findings:

```text
duplicate creation
lost update
race condition
```

Prefer deterministic setups using barriers or controlled transactions.

Avoid flaky timing-dependent tests.

---

# Phase 13 — Reproduce With Minimal Scope

The verification should target the smallest possible code path.

Bad:

```text
run entire application and inspect manually
```

Better:

```text
call affected service with controlled dependencies
```

Minimal reproduction improves confidence and speed.

---

# Phase 14 — Refutation

Verification may show the original finding is wrong.

Example:

Reviewer says:

```text
cross-tenant lookup is unscoped
```

but context reveals repository-level global tenant filter.

Result:

```text
REFUTED
```

Record why.

Refuted findings must not reach the final review.

---

# Phase 15 — Confidence Update

Verification may change confidence.

Example:

Before:

```text
HIGH / LIKELY
```

After successful reproduction:

```text
HIGH / CONFIRMED
```

After unsuccessful but incomplete verification:

```text
HIGH / POTENTIAL
```

After contradiction:

```text
REFUTED
```

Severity should not automatically change with confidence.

---

When tools or tests are executed, record the command.

Example:

```json
{
  "command": "pytest reports/verification/42/tests/test_cross_tenant_access.py -q"
```

# Phase 18 — Preserve Raw Output

Store raw tool output under:

```text
reports/raw/<pr-id>/
```

Possible examples:

```text
pytest-verification.txt
semgrep.json
bandit.json
mypy.txt
migration-test.txt
```

Do not mix raw output with final review prose.

---

# Phase 19 — Tool Failure Handling

If a tool cannot run because of:

```text
missing dependency
environment error
service unavailable
unsupported configuration
```

use:

```text
VERIFICATION_FAILED
```

Record the reason.

Do not mark the finding as VERIFIED.

---

# Phase 20 — Environment Setup Limits

Avoid large or risky environment changes merely to verify one finding.

Prefer existing project tooling.

Do not:

* upgrade unrelated packages;
* modify production configuration;
* install unnecessary infrastructure;
* change system-wide settings.

---

# Phase 21 — Verification Safety

Never:

```text
delete real data
send real email
charge real payment methods
call destructive production APIs
use production credentials
run active attacks against unauthorized systems
```

Use mocks, test doubles, synthetic data, local services, or containers.

---

# Phase 22 — Security Verification

Security verification should prove behavior without escalating beyond what is needed.

Example:

To confirm authorization bypass:

```text
attempt unauthorized access
```

There is no need to modify or destroy the target resource.

---

# Phase 23 — Secret Handling

If verification touches secrets:

* redact values;
* do not persist full credentials;
* do not echo tokens in logs;
* use synthetic credentials where possible.

---

# Phase 24 — Verification Budget

Not every finding deserves expensive verification.

Prioritize by:

```text
severity
confidence
user impact
verification cost
```

Example:

```text
HIGH + easy to verify
→ verify immediately

LOW + expensive environment setup
→ may remain UNVERIFIED
```

---

# Phase 25 — Cross-Reviewer Confirmation

Two AI reviewers agreeing is not deterministic verification.

Example:

```text
code-review says issue exists
security-review says issue exists
```

This improves signal, but does not automatically mean:

```text
VERIFIED
```

Use independent evidence.

---

# Phase 26 — Test Result Interpretation

A failing generated test must be inspected.

Possible causes:

```text
PRODUCT_DEFECT
TEST_DEFECT
ENVIRONMENT_FAILURE
CONFIGURATION_FAILURE
UNKNOWN
```

Do not automatically classify every failing test as proof.

---

# Phase 27 — Positive vs Negative Verification

Verification can be:

```text
POSITIVE
```

Proves the problem exists.

or:

```text
NEGATIVE
```

Provides evidence that expected protection works.

Example:

```text
cross-tenant request returns 403
```

may refute the original vulnerability.

---

# Phase 28 — Verification Reproducibility

A VERIFIED finding should ideally be reproducible by another engineer.

Prefer evidence containing:

```text
command
input
expected output
actual output
relevant code location
```

Avoid subjective descriptions.

---

# Phase 29 — Verification Independence

Do not rewrite the finding to make the verification succeed.

The verifier must independently evaluate the original hypothesis.

If evidence does not support it, mark it REFUTED or UNVERIFIED.

---

# Phase 30 — Finding Deduplication Support

Verification may reveal that multiple findings are the same root cause.

Example:

```text
SEC-002
CODE-004
TEST-003
```

all relate to:

```text
missing tenant scope
```

Mark the relationship for `review-synthesis`.

Prefer:

```text

```

## Queue defect

Prefer:

```text

```

When evaluating PR Guardian itself, useful metrics include:

```text

```

Example:

```text

Verified:             9

Unverified:           2
```

---

# False Positive Reduction

Calculate:

```text
refuted findings
----------------
findings verified
```

carefully and describe the methodology.

Do not manufacture percentages from incomplete data.

---

# Finding Update Rules

The verifier may update:

```text
confidence
verification_status
verification evidence
```

It should not silently change:

```text
category
severity
original finding description
```

If the original finding itself was malformed, report that separately.

---

# Synthesizer Handoff

For every finding provide:

```text
publishable: true/false
```

Suggested logic:

```text
VERIFIED
→ publishable

NOT_APPLICABLE + CONFIRMED direct evidence
→ publishable

UNVERIFIED + HIGH signal
→ potentially publishable with uncertainty

REFUTED
→ not publishable

VERIFICATION_FAILED
→ publish only if existing evidence is strong and uncertainty is explicit
```

Final publication decisions belong to `review-synthesis`.

# What This Skill Must Not Do

Do not:

* attempt to maximize confirmed findings;
* modify production code;
* force generated tests to fail;
* hide refuted findings;
* treat AI consensus as proof;
* use production infrastructure for verification;
* perform destructive security exploitation;
* publish GitHub review comments directly.

---

# Completion Criteria

The skill is complete when:

* relevant findings are prioritized;
* each selected finding has a verification method;
* deterministic evidence is collected where practical;
* generated tests are executed when appropriate;
* findings are marked VERIFIED, REFUTED, UNVERIFIED, NOT_APPLICABLE, or VERIFICATION_FAILED;
* raw evidence is preserved;
* metrics are persisted;
* publication guidance is provided to review synthesis.

# Engineering Principle

A reviewer is allowed to be uncertain.

The verification layer exists to reduce that uncertainty.

The goal is not:

> Make every finding look correct.

The goal is:

> Independently determine which findings are supported strongly enough to influence a developer's Pull Request decision.
